# REA 增量试验：本地笔记导入

本轮选择 Cherry Studio 1.9.13 的一个窄任务：Markdown 导入 → 应用读回 → 导出 → 字节核对。安装包声明的 OpenAPI 路径清单有 Agent、会话、聊天、知识库等功能，但没有该笔记导入任务；这只是对本机版本和已检查入口的结论，不声称该应用完全没有 API 或 CLI。

## 分析前后发生了什么

| 阶段 | 已获得的证据 | 仍不能得出的结论 |
|---|---|---|
| 分析前 | 已知 Electron 包身份及 preload 存在 | 不知道业务方法、参数及运行时是否可用 |
| REA 6.4.0 | 对精选 package/preload 做 AST 分析，定位两个桥接 API、327 项 IPC 操作及相关源码位置 | 324 项通道表达式未解析，exposed_api_members 为 0；不能自动生成完整接口 |
| 补充包内阅读 | 恢复相关方法签名、枚举通道、主进程注册和导入路径规则 | 普通代码阅读不能计入 REA 自动恢复率 |
| 真机执行 | 自写执行器绑定本次进程、精确应用页面和独立 profile，调用原应用桥接完成任务 | GUI 编辑器画面、个人 profile、升级兼容和 MCP 未验证 |

REA 返回的图覆盖为 **partial**；只分析精选文件，未分析完整 main/renderer。原始 Evidence 和应用源码留在本地。REA 的可证实价值是提供结构化候选和源位置；本轮成功依赖后续代码检查与实际执行验证，尚不能宣称“一键自动生成 CLI”。

## 实机结果

两份不同合成中文 Markdown 在两个新建 profile 中成功；应用回读、应用目录响应、磁盘字节和导出字节均匹配。调用真实应用后端，不使用模拟实现，也不直接写内部数据库冒充导入。

| 执行 | 文件可交付 | 导入、读回、导出 | 含退出清理总时长 |
|---|---:|---:|---:|
| 1 | 6.038 秒 | 0.092 秒 | 8.162 秒 |
| 2 | 3.506 秒 | 0.107 秒 | 4.025 秒 |

计时从 CLI 启动开始，包含摘要预检及应用启动，不包含 Agent 首次分析开发时间。两次运行不代表稳定均值。校验通过即输出文件就绪事件，应用退出清理随后执行。

重复运行目录、缺失输入和错误格式被拒绝；既有产物没有改变，错误输入没有新建运行目录。固定安装包摘要用于阻止未知版本。两个测试进程已退出，profile 留作本地证据。userData 隔离不是 OS 文件系统沙箱，不能保证应用完全不访问共享宿主路径。

## 对通用工具的改进

- 增加 `summarize_rea.py`，将大体积 REA JSON 筛成覆盖范围、计数和选中源位置，降低 Agent 读取和往返成本。它是开发摘要，不验证 Evidence 密码学真实性，也不能当作脱敏发布器。
- 明确分开 REA 静态发现、普通包阅读和运行时验证，保留 partial/dynamic 信息。
- 将“存在官方 API”改为任务级判断：仅当它能完成当前任务时优先复用。
- 把 profile、监听 PID、页面和实际数据目录的核对放在动作之前，文件校验完成立即交付。

下一里程碑是同一适配器的重启读回与升级失效演练。先巩固维护能力，再增加更多应用；当前结论限于已验证的窄任务。
