# 第五款应用：从静态接口到生成 CLI

目标是减少制作 CLI 时重复分析、抄写桥接方法与参数的步骤。本轮选择 Hydrogen Music 0.6.2 的本地播放队列保存/读取；安装包元数据未声明 CLI bin 或脚本字典，已检查主进程启动入口未发现这项业务的命令行路由。这是对本机版本、指定任务和已检查范围的结论，不声称不存在任何外部适配器。

## 本次自动化的部分

新增保守 AST 提取器，从 REA 对应精选源码中恢复函数声明、对象 shorthand、简单箭头和字面量 IPC 的映射。要求源文件摘要和调用位置与 REA 观察匹配，不执行提取源码。此次得到 **83 个候选、40 个 unsupported**；REA 覆盖为 partial，不等于完整应用已解析。

显式选择保存、读取、退出三个方法后，生成器产出窄 CLI，调用原 preload 方法。这三个实际验证的方法的路径、形参、数量和传输方式全部来自提取结果，**手写桥接映射为 0**。应用专用契约、生成产物、启动器和原始证据没有进入公开仓库。

本轮选择目标时已查看桥接和存储逻辑，属于开发样本验证，不是盲测。自动工具并未消除业务理解：人工仍确认队列数据结构、私有 profile 启动/清理方式、成功条件和重启步骤。

## 真实结果

通过生成的 CLI，保存两段自制静音 WAV 的合成播放队列；应用读回的顺序、曲目字段、当前项和进度均与输入一致，独立读取该 profile 的持久化文件也匹配。退出后用原 profile 启动新进程，未重新保存队列，应用读回和文件再次匹配。两个自有实例及调试端点均已退出，未播放或下载第三方音频。

CLI 对 send 只返回 `dispatched`，对 invoke 返回 `returned`，两者始终 `verified:false`。任务包装器通过应用读回与独立文件验证后才记录业务 verified。参数数量错误、未选方法均被拒绝；第一次启动时页面从初始 URL 导航到稳定路由，旧 URL 的调用被正确拒绝，随后固定稳定 URL 重新生成。

| 指标 | 本轮观察 | 不能据此推断 |
|---|---:|---|
| 自动候选 / unsupported | 83 / 40 | 83 项均可用或安全 |
| 显式选择 / 真实调用 | 3 / 3 | 其余候选已验证 |
| 已有源码与 REA 结果上的提取＋生成 | 5.071 秒 | 用户首次提出需求到交付只需此时长 |
| 已连接会话中的保存/读回流程（含负例） | 0.916 秒 | 包含应用启动、分析、Agent 往返 |
| 重启后的单次 CLI 读回 | 0.248 秒 | 完整重启耗时 |

再次生成的契约与 CLI 文件逐字节一致，复现不需要重新手写方法。两次生成不构成性能基准；目前没有足够样本计算人工工时下降比例。

## 通用改进及边界

- `discover_bridge.mjs` 自动提取候选；复杂/动态逻辑保留 unsupported。
- `generate_bridge_cli.mjs` 仅生成显式选择的方法，拒绝覆盖已有目录。
- `bridge_runtime.mjs` 复用兼容性门禁，核对本机进程、profile、目标和页面；实际调用前再次检查页面 URL。程序接口和 CLI 入口都限制方法集合。
- 18 项 Node 合成测试与已有 32 项 Python 测试共同进入 CI。合成测试不代替上述真实应用验收。

当前范围是 Electron 顶层 CommonJS 静态子集，macOS 运行时；不自动解决动态枚举、事件订阅、任意 GUI、native 应用或业务参数 schema。来源归属、启动隔离和验收仍需确认。下一阶段优先收集被明确拒绝的实际结构，逐类补充有证据支持的解析能力，不放宽 unsupported 为“猜测成功”。
