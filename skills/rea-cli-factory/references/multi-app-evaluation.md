# 多应用验证协议

目标是检验同一工作流在不同应用中能否得到可重复结果，不是统计静态工具找到多少函数。一次成功只覆盖指定应用版本、任务和环境。

## 先选择入口

运行 `scripts/probe_app.py --app /absolute/Selected.app` 读取包身份、摘要、有限目录中的框架和脚本字典线索。输出的候选不等于可调用接口；目录截断必须保留。此工具不执行应用、CLI help、REA 或 Apple Events。

随后按任务依次检查：

1. 应用已有 API / 命令行。查看包内 help 或官方文档，先尝试原生功能。
2. 已声明的脚本接口。读取字典后只操作自建测试对象，验证权限与结果。
3. 已知运行时桥接入口。验证进程、会话、对象身份及隔离边界。
4. 仍有具体信息缺口时才使用对应版本的 REA 静态分析，区分候选与实测。

原生入口已经满足任务时，不为增加 REA 调用次数而反编译。没有分析器证据就将 reaExecuted 标为 false；即使执行过 REA，也不能把执行前已发现的 CLI 称为 REA 增量。

## 每个试验记录

- 应用名称、版本、安装包/可执行文件摘要，主架构与调用接口。
- 一个窄任务及自建输入；预期业务结果与独立读回方式。
- 独立 profile / 项目 / 输出目录；有 GUI 时标明，保留用户原窗口和文档。
- 首次执行与重复执行耗时、成功和失败状态、产物摘要。
- 输出已存在、目标版本变化、无效输入、未授权自动化和超时的处理。
- 明确哪些入口是原生 CLI、脚本字典、普通包检查或 REA 发现。

不以进程退出 0、文件存在或截图代替内容核验。成功状态必须与真实产物一致；运行时与静态证据冲突时以本次可复核结果说明。

## 收敛与停止

先定义三个不同控制入口的样本，优先在每个样本完成一个可验证任务，而非单应用无限扩展。权限拒绝时报告 blocked，不关闭用户应用或绕过权限。重复副作用前先检查产物；无法确认时不再次提交。

有独立权限且接口清晰的应用可并行验证，但每个执行者独占自己的实验目录。应用适配器、原始包内容与用户证据默认留在本地；公开仓库只接收通用流程、工具和明确允许的脱敏结论。

多样本通过证明工作流可复用，不证明“任意应用自动生成 CLI”。仍需另行验证没有 CLI / 脚本接口的目标、升级失效和长期运行。

## 内部接口的补充验收

- 按具体任务检查官方 API 覆盖，而非按应用是否有 API 二分。记录分析前未知、REA 实际发现、普通代码补充和实际执行器的各自贡献。
- Electron 使用独立 profile 时，先检查包内启动配置是否会覆盖它，再验证监听 PID、精确页面和应用返回的数据目录；不能只相信启动参数。独立 profile 不等于文件系统沙箱。
- IPC 返回成功前后都可能有部分副作用。核对成功/跳过数量、实际产物和原始内容，避免把 Promise 完成视为业务成功。重复请求先检查已有收据和产物。
- 日常路径不重复 REA，使用已验证摘要与窄任务命令；输出 `file_ready` 后再退出自有实例，分别报告文件就绪和清理完成。
