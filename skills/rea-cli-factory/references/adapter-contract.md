# 操作契约与证据

本 Skill 借鉴 [CLI-Anything HARNESS](https://github.com/HKUDS/CLI-Anything/blob/main/cli-anything-plugin/HARNESS.md) 中的真实后端、结构化输出、已安装命令和真实产物验证方法；没有复制其模板或声明完整兼容。需要完整 CLI-Anything 格式时，读取并遵循其当前规范。

REA 的作用是提供可追踪分析证据，CLI/MCP 适配器负责动作和结果判断。参照 [REA](https://github.com/morluto/rea) 的版本匹配指引；不要混用仓库 main 的文档和旧版 CLI 的参数。

## 每项操作应回答

| 项目 | 内容 |
|---|---|
| target | 包标识、应用版本、关键文件摘要、实际运行目标身份 |
| operation | 任务名称、输入及约束、是否改变状态 |
| backend | API/脚本/IPC/文件导入/GUI，以及启动和登录依赖 |
| evidence | 来源定位、REA 实际记录引用、覆盖范围和未知部分 |
| outcome | 可读回的对象或最终产物，完成/失败/未知的判定 |
| failure | 稳定错误码、可否重试、已产生的副作用、恢复方法 |
| verification | 验证日期、版本、实际命令、结果、测试数据清理情况 |

契约可保存在 JSON 或 Markdown，按项目复杂度选择；不必为一个只读命令搭建完整注册中心。凭据和个人账号信息不进入契约。

建议成功输出包含 `ok`、`operation`、`result`、`verified`；失败输出包含 `ok: false`、`error.code`、`error.message` 和必要的恢复信息，并返回非零退出码。`verified` 表示本次结果已检查，不能由“没有抛异常”自动推导。长任务的 `accepted`/`pending` 状态应与完成分开。

## 将 REA 增量与现成接口区分

留下常规检查发现了什么、REA 额外发现了什么、哪些发现成功进入运行路径的简短记录。使用现成接口成功可以证明适配器可行；如果没有用到 REA 发现，不能据此声称验证了逆向分析的增量。

## 典型失效边界

- 发现内部函数，但它仅存在于特定进程或隔离上下文：先证明调用路径，不能直接导出同名工具。
- 请求返回成功，界面或文件尚未更新：等待有界的结果信号并读回；超时报告未知/失败。
- GUI 后端被 CLI 包装：仍需窗口、会话和目标定位；不要宣称无头运行。
- 搜索返回登录页或网络错误页：失败，不当作零结果。零结果需有页面或 API 的明确证据。
- 新版本 hash 改变：受影响的内部入口重新分析和验证；不要静默放宽版本约束。
- 测试对象与用户原有对象混在一起：仅删除有本次创建收据的对象，保留用户状态。
